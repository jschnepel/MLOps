# Problems found, and what changed because of them

This project began as an AI-generated build package. Before writing any code, the plan went through six adversarial review rounds (`docs/reviews/`), each with fresh reviewers told to assume every claim was false until shown evidence. This page lists the problems those rounds found and how the design changed. It is written for a reader who wants to know what engineering judgement went into the plan, not only what the plan says.

Each entry gives the problem, where it was found, and the change. The round number points to the review file with the full finding.

## 1. The diagrams had the pipeline backwards

**Problem.** The overview diagrams showed the LLM reasoning first, choosing its own tools, and then handing "tool call intents" to the tool layer. The detailed specs said the opposite: the workflow engine retrieves evidence first, then the model drafts from that evidence, and the model never chooses tools. (The diagram comparison that preceded round 1; round 1 recorded the same ordering error in the package.)

**Change.** The detailed specs were adopted as authoritative and the overview diagrams were marked for correction. The runtime order is fixed as: admit → retrieve through controlled tools → draft → independent review → guarded write → receipt-backed result.

## 2. A crash at the wrong moment left a run stuck forever

**Problem.** The reference implementation marked a run "executing", then called the incident service. If the process died between those two steps, nothing could ever move the run again: re-execution was refused and reconciliation raised without saving state. The spec defined recovery for only one of four crash windows. (Round 1.)

**Change.** An explicit attempt protocol: *intent* (grant recorded, nothing sent) → *sent* (request definitely left) → *resolved*. Each window has a defined recovery. A never-sent action can be closed for certain through an **abort tombstone** at the destination, so "no incident exists" is a provable state, not an assumption.

## 3. "Exactly-once" was promised and cannot be delivered

**Problem.** The marketing diagrams said "ensure exactly-once semantics". There is no universal exactly-once guarantee across arbitrary services. (Round 1.)

**Change.** The system is honest about uncertainty: an action can end **unknown**, then **escalated**, then (by an audited operator decision) **abandoned-unverified**. The destination owns the truth through an idempotent action key that is never deleted. Retries always reuse the same key; nothing is ever retried under a new identity.

## 4. The write-fencing did not actually fence

**Problem.** Fences were per job, but the work was per run, so two workers could both believe they owned a run. The fence check was a plain read, which a stale worker could pass. Expiry checks used `now()`, which PostgreSQL freezes at transaction start, so a slow transaction could pass a check after its lease had expired. (Per-job fencing: round 1; the lock and clock defects: rounds 2–3.)

**Change.** One lease and one monotonic fence **per run**; every fenced write first locks the lease row (`FOR SHARE`, acquisition `FOR UPDATE`); all time comparisons use `clock_timestamp()` after locks are taken; one published lock order; the heartbeat runs on its own thread and connection so a long model call cannot lose the lease.

## 5. The checkpoint library behaved differently from what the spec assumed

**Problem.** The spec assumed graph checkpoints were written before the next step. LangGraph's default is asynchronous: it persists *while the next step runs*. Resuming from a stored checkpoint ID re-runs already-finished tasks instead of restoring their writes, and a crash-recovery resume forks the checkpoint. The library has no option to put its tables in a separate schema. (The custom-saver need: round 1; durability, resume and schema: rounds 2–3 and 5, verified in the library source.)

**Change.** Synchronous durability is required; the accepted checkpoint ID is stored on the run and read only after the library confirms it; every node must be idempotent; the saver's schema is set through the connection's search path. Version 1 runs a single worker replica and says so, instead of claiming fenced multi-worker checkpoints it cannot prove.

## 6. The tool server would have held the keys to the authority tables

**Problem.** The MCP tool server, the most network-exposed internal service, was specified to perform the final execution grant itself. That required write access to the approval, membership and grant tables, across tenants. (Rounds 1–2.)

**Change.** The tool server's database role has **no table access at all**. It can only execute a fixed set of `SECURITY DEFINER` functions that resolve its capability handle, perform the grant, record each attempt step and read tenant-filtered evidence. Later rounds found the first version of this design could not even run the system (the API could not create jobs; the worker could not update runs) and had no row-security policy for the function owner. The 1.3.3 rewrite replaced the prose matrix with exact column-level grants, a function-contract table (callers, inputs, locks, transitions, events), append-only state rows instead of updates, and explicit policies. Every state transition and every event now goes through a function.

## 7. The worker wrote its own tool allowlist

**Problem.** The party being restricted (the worker) chose which tools its capability handle was allowed to call. (Round 1.)

**Change.** The allowlist is derived on the server from the job type, the run state and the attempt state. Job types themselves were undefined until round 5; they are now a table with creator, purpose, allowed tools and dedup keys.

## 8. The local model needed settings nobody had measured

**Problem.** `qwen3:8b` "thinks" by default; thinking tokens would eat the output budget and leak reasoning the spec forbids showing. No context window was set (Ollama defaults to 4k on this GPU). A cold model load measured 53 seconds against a 60-second timeout. (Rounds 1, 4.)

**Change.** Thinking is explicitly disabled and verified; the context window is explicit; a warm-up call runs at worker start and verifies the pinned model digest; a measured probe on 30 distinct inputs precedes any use of the model, and its result is an owner decision rather than a fixed gate the probe could not justify statistically.

## 9. Identity revocation was not what the spec thought

**Problem.** Disabling a user in Keycloak does not trigger back-channel logout; the auth library has no helper for it; introspection is audience-checked in current Keycloak; the MCP SDK's built-in audience check expects a URL, not a client ID; token issuer differs between host and container callers. (Disable ≠ logout: round 1; the rest: rounds 2 and 4.)

**Change.** Decision-class actions check the user's status through the admin API with a fail-closed timeout; a membership sync bounds the window; audiences are resource URLs; the Keycloak hostname settings that make the issuer identical were verified in a live container before being written into the plan.

## 10. The evaluation could not support its claims

**Problem.** The test corpus was 463 words, smaller than one planned chunk. Only 2 of 32 scenario cards exercised the model. With 25 holdout cases, differences under about 30 points are not reliably detectable; the amendments had first written 15–20, a figure the round-2 review itself introduced and round 3 corrected. Repeated trials were clustered and the 2-of-3 rule inflated rates. The owner would author the holdout, write the manual baseline and label the outputs, so the comparison was biased. A hash proves a holdout was not edited, not that it was not seen. (Rounds 1, 3, 5.)

**Change.** A larger corpus; the deterministic scenario suite is separated from the model-quality evaluation; case-level Wilson intervals and paired McNemar tests; safety metrics fail a case on any single bad trial; the manual condition is scored only with deterministic metrics; labelling is blind; the holdout is written before any prompt tuning, kept off the machine, and its hash is recorded outside the repository. The README is required to state the 30-point detectability floor.

## 11. The second-incident guard missed the common case

**Problem.** Two conversations could both be approved for the same asset and time window. The first guard blocked only *unresolved* actions, so once the first incident succeeded the second was created. The next version blocked only incidents committed *after* the second proposal froze, which is the uncommon ordering. (Rounds 5–6.)

**Change.** A grant is refused whenever any committed incident overlaps the same tenant, asset and interval, regardless of timing, unless the proposal explicitly names the run it supersedes and the reviewer approved that payload. Refusals move the run back to review rather than leaving it stuck holding the conversation slot.

## 12. The task plan could not be executed in order

**Problem.** All 32 tasks formed one serial chain; requirements were scheduled before the capabilities they test existed; every task had the same copied definition of done; evaluation sat behind Kubernetes and restore drills; nothing was showable until the last tasks. Later, three tasks had grown to between 4 and 14 days each. (The serial chain: round 1; placement and the walking skeleton: round 3; the splits: round 6.)

**Change.** A dependency graph; each requirement placed where it first becomes testable; a walking skeleton through every service before any hardening; early secret-free CI; the holdout sealed first; oversized tasks split; a critical path of 15 tasks.

## 13. Library facts were stale or wrong

**Problem.** The MCP import in the example code did not exist in the current SDK; the spec described an older handshake model; it recommended a network plugin that the local Kubernetes tool does not support; the model-integration dependency was missing from the manifest; there was no lockfile. (Round 1.)

**Change.** Every library claim was checked against live sources or downloaded package source, exact versions were recorded, and the stale examples were marked historical.

## 14. The plan's own documents over-claimed

**Problem.** The README, the start guide and the agent prompt said "tested Kubernetes deployment" and "production-ready"; the first git commit labelled "unmodified" had one modified file; an edit of mine corrupted a rule by writing a real line break where the literal `\r` belonged; the machine's local model server was listening on every network interface with permissive firewall rules. ("Production-ready": round 1; the rest: rounds 5–6 and the environment checks.)

The author's own mistakes, in the order found: the first amendment (1.1) introduced three critical defects of its own (round 2); the checker read files without an encoding under a cp1252 locale (round 4); an ADR and the amendments disagreed about which task moves the reference code (rounds 3 and 7); the README sentences stating the plan's limits were lost in a rewrite and only restored after round 7; the "unmodified" import commit had one modified file (round 6); a carriage-return escaping error corrupted a rule (round 5); the showcase document described unwritten code in the present tense and cited a test that cannot exist for a host-side process (round 7); the first implementation plan asserted "passed" and "GREEN" outcomes for steps the author had never run, nine of which failed when a reviewer executed them on scratch copies (round 8).

**Change.** The entry documents now state that implementation has not started and make no Kubernetes claim; the original package is committed as a zip and verified byte-for-byte; the corruption was fixed and a no-carriage-return check added; the network exposure was reported to the owner, who chose to restrict it (the runbook is a task; the agent changes no system settings).

## 15. The four concepts the project exists to show were not visible

**Problem.** After six rounds the plan specified least privilege and the orchestrator in detail, but nowhere a reader could find them; routing existed only as scattered rules; and one MCP server hosted both reads and the guarded write, which hid the privilege story behind a single process and database role. (Owner review after round 6.)

**Change.** Three named routers with enumerable route tables and their own requirement (admission, graph, model); the MCP server split into `mcp-read` and `mcp-write` with disjoint database functions, audiences and handle types; and `docs/ARCHITECTURE.md`, which maps each concept to its components, the requirement IDs that prove it and the demo that shows it (ADR-0003).

## 16. The first slice passed its task reviews and still failed its final review

**Problem.** Plan A (baseline, sealed holdout, model probe, reference move, uv workspace, CI) was executed task by task, each task by a fresh implementer and gated by a fresh reviewer; all six gates passed. The whole-branch review that followed still found five defects that no task-scoped review could see: the checker that was supposed to guarantee "nothing under `reference/` differs" only covered the 19 hash-pinned files, and a reviewer proved it by editing, deleting and adding files under `reference/` with the checker still exiting 0; the advertised one command was RED on a fresh clone because the virtual workspace root only synced the dev group; the probe would have reported `0 MB` of VRAM as a measurement when `nvidia-smi` was absent and measured a configuration without the structured-output wrapper the spec names; and the handoff state still told the next session to start at task one. (Plan A final review, 2026-10-07.)

**Change.** A whole-tree integrity check (`provenance/reference-tree.json`, every delivered file byte-compared with the zip, no extra files, remap targets confined to `reference/`) with five tamper tests; the root depends on every member so `uv sync --locked` then `uv run python scripts/check.py` is green on a clean clone; the probe samples VRAM during calls and says "not measured" when it cannot; the probe measures `with_structured_output(method="json_schema")` plus application-side validation; task statuses `DONE` and `DONE_PENDING_OWNER` replaced a vocabulary that had only `PLANNED`. The lesson kept: task gates catch task mistakes; only a review of the whole branch catches a guarantee that no single task owned.

## 17. The bootstrap plan was wrong in the places only a real machine can show

**Problem.** Plan B (Compose dev profile, Keycloak realm, personas, Ollama bridge) was written from the real Plan A artifacts and self-reviewed, then put through two adversarial critics before anyone executed it. The static critic found that the model-pins loader would reject the digest the probe actually writes (Ollama reports a bare 64-hex digest; the loader demanded a `sha256:` prefix), so the worker would have failed closed forever; that the Keycloak readiness probe grepped the body for `"UP"`, which a DOWN response also contains; that rotating the PostgreSQL password by deleting its file does nothing on an initialised volume; that audience assertions used "contains" and would have missed an extra audience — the token-confusion case the spec names; that a wildcard redirect URI contradicted the spec's "exact redirect allowlists"; that the firewall runbook assumed a source address nobody had measured; and that the realm placeholders shared Keycloak's `KC_*` option namespace. The builder critic, who executed every step on a scratch worktree with real Docker, found that every Keycloak assumption held (placeholder substitution, seeded IDs, identical `iss`, the service account's 403s, the bootstrap admin's self-deletion) but that the plan's Python was not ruff-formatted, so three of its four "CHECK: GREEN" claims were false, and that Keycloak answers a deleted user's password grant with 400, not the 401 the plan asserted. (Plan B review round 1, 2026-10-08.)

**Change.** The loader accepts the digest format the probe writes and a test pins the exact file shape; the healthcheck reads the HTTP status line; the rotation procedure says `ALTER ROLE` or a deliberate volume reset; audience sets are compared exactly; the redirect is the exact callback; the plan measures the container's source address with `Get-NetTCPConnection` while a helper container holds a connection, and the runbook reasons from the measurement; placeholders moved to `OPS_KC_*`; every Python block was passed through the repository's formatter before the plan was re-reviewed; the 400 is recorded as a measured fact. The second dry run, of the corrected plan, then overturned a premise everyone had accepted since the first environment check: on this Docker Desktop a container's connection to `host.docker.internal` arrives at the host from `127.0.0.1`, proxied by Docker's backend, so the firewall rule scoped to the WSL subnet that the owner had chosen would have admitted nothing, and binding Ollama to loopback — the simplest control, which the earlier reasoning had rejected — is the one that works. The runbook now leads with the measurement and the loopback bind, keeps the firewall rule as a fallback, and proposes the spec errata for the owner. A third, closing check then caught that the runbook's bind command targeted the Machine-scope environment while `OLLAMA_HOST` was set at User scope — a command that would have run without error and changed nothing. The pattern from the earlier rounds repeated exactly: the reviewer who ran the plan found different defects from the reviewer who read it, and both were needed.

Executing the reviewed plan still produced findings at every task gate, all in text the plan had mandated: a password-rotation recipe that claimed the value never touched a command line while passing it in `psql`'s arguments (replaced by a stdin-only form); a test meant to catch a committed literal secret whose own failure message would have printed that secret into the CI log (the first fix, a custom assert message, did not work, because pytest's assertion rewriting still prints the operands; the final review caught it, and the tests now assert on a precomputed list of identifiers, with proof tests that tamper a copy and check the literal never reaches the failure text); and a runbook fallback that would have created a duplicate firewall rule on every re-run and pointed the owner at a plan step they do not have (now self-contained and re-run safe). An automated security review also caught that the generated secret files were created with default permissions; they are now owner-only and created with `O_EXCL`.

## 18. The contract plan was wrong about its own spec in four places

**Problem.** Plan C (core contracts, schema alignment, reference traceability) was written from a line-by-line inventory of the spec, the delivered schemas and the 58 reference tests, and its first four tasks were run on scratch copies before anyone reviewed it. The reviews still found that the planner's transition table let a frozen proposal be blocked for reasons the spec reserves for the grant, that the mapping from a destination's ABORTED tombstone to a reason ignored whether the request had ever been sent, that the "redacted" style of failure message from Plan B had been reused in a test where pytest's assertion rewriting would print the value anyway, and that the checker could not import its new helper under `python -I` — a failure that would have broken CI and nine existing tests. The static critic also measured that the installed JSON-Schema validator never checked `date-time` at all (no `rfc3339-validator`), so `"occurred_at": "yesterday"` validated, and that the delivered tool-result schema accepted an `ok` envelope carrying an `UNKNOWN` outcome — the exact contradiction R083 exists to forbid. The plan had described twenty-five JSON Schemas in prose; the builder critic, executing it, had to invent every ambiguity and wrote a generator instead. (Plan C review rounds 1–2, 2026-10-08.)

**Change.** The reason sets now follow AM-10 row by row; the outcome mapping is keyed on the attempt state at abort; the schemas are produced by a committed generator with a drift test, so there is one source of truth for 25 schema files, 68 examples and the index; `rfc3339-validator` is a dev dependency and a probe proves it; every negative example must fail *for its stated reason* (a regex on the validator's best-match error), which caught two probes that failed for the wrong reason; the checker puts the repository root on `sys.path` and CI runs it through `uv`. Five self-contradictions found in the spec while modelling it — which states a revision may leave, whether `expired` is a no-commit reason, two spellings of the retrieval mode, a transition BUILD_SPEC lists but the amendments forbid, and cancellation from a state that holds no slot — are ruled in the plan header and proposed to the owner as errata rather than silently chosen.

**Problem.** The contract work then ran the way the process says it should, and still found the plan wrong about its own spec. Six of the eight implementation tasks needed a fix round; the fixture-metadata and traceability tasks did not. The first canonicaliser let a bare `ValueError` or `RecursionError` escape instead of its own error on oversized integers and deeply nested input. The first transition table had no performer for `create_manual_proposal`, and it did not pin each row's reason set. The key patterns were anchored with `$`, which tolerates a trailing newline, and the shape of the sweep bucket was never validated. The serious one was in the contracts: uniqueness and sort order were checked on the raw strings while the hash is computed on NFC-normalised bytes, so two payloads that are the same text after normalisation could hash differently. That is the property (R005) the whole design rests on, and it was a Critical. Around it sat three smaller defects: duplicate JSON keys silently kept the last value, a cancel response could claim two contradictory states, and an epoch-seconds string passed as a timestamp. Later the outcome schema did not pair a late-evidence outcome with its receipt or tombstone, although the code did. Modelling the spec also produced nine rulings in all, four of them real contradictions inside the documents (rulings 1, 2, 4 and 7) and four readings the spec leaves open (rulings 3, 5, 6 and 8); the ninth, the missing performer, came from the Task 2 review. The tooling had its own surprises. The JSON-Schema format checker did not check `date-time` at all until `rfc3339-validator` was installed, so a malformed timestamp validated. The R083 probe `event-invalid-confirmed-no-receipt` validated against the delivered 1.0 schema, which is exactly the contradiction it was written to forbid. The index recorded which examples failed but not why. The hand-edited schemas drifted from the code until they became output of a generator. And the first run of the conformance test found the schema and the code disagreeing on one example: an `action.conflict` event carrying an `outcome` was rejected by the schema and accepted by `event_rules_ok`. The schema was right (AM-14 lets only confirmed, failed and late-evidence events carry outcome evidence), so the code was tightened, which is what the test exists to catch. The plan's expected pytest totals also drifted by 39 across the run, because every fix round added tests. (Plan C execution, T07, T45 and T46, 2026-10-08.)

**Change.** Canonical JSON now raises its own error for every input it refuses, and normalises strings to NFC before it checks uniqueness, order or length, so equivalent payloads hash alike; duplicate keys, contradictory cancel responses and epoch-string timestamps are rejected, and the dedup-key patterns in `jobs.py` use full matches. The transition table has 44 rows, 38 distinct pairs and 13 performers, with every row's reason set pinned. The outcome schema ties a late-evidence outcome to its receipt or tombstone. At the end of the plan the generated tree was 25 schemas and 68 examples (30 valid, 38 invalid; two negatives were added in the schema task's fix round), and `date-time` is checked for real. Each negative example has to fail for its stated reason, and the index now records the reason. The schemas come from one generator with a drift test, and a conformance test runs the generated examples through the pydantic contracts (69 cases at that point, 18 skipped with stated reasons for the tool inputs and routes that later tasks consume). The nine rulings are written up in `SESSION_STATE.md` as proposed errata; the owner decides, and the spec stays authoritative until then. The ledger tracked the test-count offset instead of forcing the totals to match the plan.

**Problem.** The whole-branch review after the last task gate found the seams that no single task could see, because each task review saw only its own side. Two of the "now raises its own error" and "full matches" claims above were not yet true: `canonical_json` recursed outside its `try`, so JSON nested 2000 deep passed the strict parser and then escaped as a bare `RecursionError`, and every schema pattern ended in `$`, which Python's `jsonschema` lets match before a trailing newline, so `"A17\n"` and `"…Z\n"` validated while the code refused them. `CancelResponse` refused the truthful report for a run that had failed before any grant, because its post-grant set included FAILED. `dedup_key` let `INVESTIGATE(run, revision=2)` and `RESUME_INPUT(run, clarification_event_id=2)` mint the same key in a column that is globally unique, so the second job would be dropped silently. Probing every combination found 113 of 340 cancel responses on which schema and code disagreed (the schema accepted an "undo" claim), `action.failed` with reason `conflict` accepted by the schema alone, and an outcome schema that allowed a REJECTED tombstone with any reason. None of this was visible to the conformance test, because it only replayed the examples someone had written down. (Plan C final review, 2026-10-08.)

**Change.** `canonical_json` normalises inside its `try`; FAILED left the post-grant set, and a grant is refused with any state no grant can precede (the pre-grant states plus REJECTED, ANSWERED and INSUFFICIENT_EVIDENCE); dedup keys take UUIDs and a positive revision and raise their own error. The generator mirrors every cancel-response rule from the same state sets the code imports, restricts `action.failed` to the no-commit reasons, pairs REJECTED tombstones with `rejected` in both directions, and ends every pattern with `(?![\s\S])`, which means "nothing follows" in both ECMA-262 and Python; fixed-length strings carry `maxLength`. The conformance test now also mutates every valid example of a modelled schema (each enum value, each boolean, each required key; 326 mutants) and requires schema and code to agree. Its first run found two more seams: events missing their envelope fields (the code had no event model yet, so a small strict `Event` model now holds the envelope and runs the authority rules) and a malformed tombstone on `action.failed`, which the schema refused and the code passed; the related case of a late-evidence event carrying both kinds of proof was closed in the same change. The tree is now 25 schemas and 87 examples (34 valid, 53 invalid). The decisions the review raised for the API boundary (the bytes a stored proposal hashes, null and whitespace conventions, timestamp edge cases) are recorded as open items for Plan D rather than settled here.

## 19. The skeleton's plan was measured before it was written, and still needed three rounds

**Problem.** Plan D (the walking skeleton: five processes, real tokens, one run end to end) was the first plan whose libraries the project had never run — the MCP SDK's 2026 protocol, PyJWT against Keycloak's key set, psycopg's async driver, Alembic driven from Python, FastAPI behind a bearer dependency — so before any plan text existed a fact sheet cited 102 spec requirements with line numbers and a spike measured each library seam against the live dev stack. The spike was right about most things and wrong about one: it read uvicorn's source and concluded the server picks a selector event loop on Windows; it picks the Proactor loop, which the database driver refuses, so every service the plan started would have died in its first second. The static critic measured that; the builder, executing all nine tasks on a scratch worktree, hit it as "mcp-read exited early" and twenty workarounds besides. The worst were not about libraries at all but about transactions: a connection opened without autocommit turns every later unit of work into a savepoint inside a transaction that a bare `SELECT` left open, so mcp-write granted, marked SENT and recorded a receipt that was never committed, and incident-sim answered `COMMITTED` for a key that vanished when the process stopped — the end-to-end test passed anyway, because it read the application's view and never the destination's. The same shape wedged the worker when its health probe shared the poll loop's connection: ready, forever, and doing nothing. Alembic tried to create its version table in a schema the first revision had not yet created; a strict pydantic model refused the UUID text every valid request carried; a FastAPI dependency named through a local alias under `from __future__ import annotations` became a required query parameter, so every protected route answered 422; live tests claimed to roll back and committed instead, leaving jobs for the real worker to pick up during the next test; and an error that escaped the MCP client's context arrived wrapped in an exception group that nothing caught, so a transport failure left the run in RETRIEVING with its conversation slot held.

**Change.** Every process now serves uvicorn programmatically on a selector loop, holds one autocommit connection wrapped in a `Session` (a lock plus an explicit transaction per unit of work, so SENT is durable before the first byte leaves and a receipt means a committed key), and the worker's readiness has its own connection and turns 503 when the poll loop stops. The version table lives in `public`; request bodies are parsed in JSON mode after a strict duplicate-key gate; dependencies are declared inline with no future import; the destination hashes the payload's bytes exactly as received, carried as one JSON string; live tests roll back by force or purge what a second process had to see, in-process servers bind ports the skeleton never uses, and the end-to-end module owns its process fixture so the real worker is down before other tests claim jobs; the MCP client flattens exception groups to the transport failure underneath, with a unit test against a closed port. The plan gained six rulings (the reviewer's proposal document, the event-loop rule, the connection rule, 401 for every refused token, where unit tests live, what live clean-up may delete) and three more declared shortcuts, and its review record keeps all three rounds. The third round found nothing blocking and nothing important, and the builder's end-to-end run reached SUCCEEDED with the nine events, a replay that returned the same action id, and every wrong token refused. (Plan D review rounds 1–3, 2026-10-08; `docs/reviews/plan-review-d-2026-10-08.md`.)

**Problem.** The execution found less than the planning had, and the reviews still earned their keep. Every task passed its review on spec; seven of the eight implementation tasks needed a fix round (only Task 1 did not) and Task 7 needed two. Across all of them the task reviews found no Critical and eight Important findings, which come to five distinct issues. The token verifier's key-set refresh was unbounded on a failing fetch and had no single-flight, so ten concurrent requests with an unknown key made ten fetches. Four lines the plan dictated in the migrations ran past 120 columns. And mcp-write's write path could interleave between units of work when two calls raced for one run (two SENT rows, a second POST, a failing second transition), while an exception that was not a transport error, raised after the grant, escaped the tool instead of recording OUTCOME_UNKNOWN. An automated security review of the API's own planned code caught two tenant-scoping seams that the human reviews had not: a subject with memberships in two tenants would have received the union of their roles, and a requester-asserted `supersedes_run_id` was stored without checking that it named a run of the same tenant and conversation. The minors were mostly the comment standard (one-line docstrings on every public definition), strict argument models (a UUID tool argument needs lax parsing of its text), explicit error bodies for malformed path ids, and connections closed at shutdown.

**Change.** The reviewers did not stop at reading: their live probes confirmed what the plan had promised. SENT was durable before the first byte left, seen from a second connection; one grant per run held under concurrent calls; a transport failure or a drafting error failed the run instead of stranding it; the destination's receipt stayed the same across replays; a persona token was refused at every MCP server and a workload token at the API. The tree now proves the R105 run end to end against the running dev profile: alex asks, the worker reads one procedure through mcp-read and drafts with the fake model, sam (not the requester) approves the frozen proposal, mcp-write grants, marks SENT and posts, incident-sim answers with a receipt, and the run ends SUCCEEDED with nine events, the last written from the destination's answer. The refusals are part of the same test: the requester deciding on their own proposal (403), a stale hash (409), a second decision (409), a replayed `create_incident` returning the same action id and the same receipt, and the wrong tokens at the API, the destination and mcp-write. The live suite passes with fourteen tests, and the evidence file records the run (`reports/skeleton/r105-walking-skeleton.txt`).

## 20. What the process taught

Eight spec rounds and four plan dry-runs found the following pattern: each round's fixes introduced the next round's high-severity findings, because new mechanisms (functions, tombstones, locks, matrices) arrive with their own gaps. The fourth and eighth rounds, which executed the first tasks on the real machine instead of reading them, produced the findings that changed the first slice most, and the Plan B dry-run did the same for the bootstrap. Every implementation plan is now dry-run on scratch copies before anyone executes it, and every executed slice gets a whole-branch review after its task gates. The plan therefore ends spec-wide review here and reviews each implementation slice against its code and tests, where a grant either lets admission commit or it does not.
